# MVP 路线图 V1

## 当前推荐方案

本项目当前采用：
- 分层文档
- 混合型数据库设计
- 先冻结目录与数据边界，再进入代码骨架实现

## 为什么选这个方案

### 不选更轻的方案
如果只做一份总文档、只设计极少数表，后面在这些场景会很快返工：
- 多语言搜索
- 歌曲与作品多关系
- 专辑版本
- 用户收藏与歌单

### 不选更重的方案
如果一开始就上：
- 通用翻译表
- 超规范化数据库
- 很重的架构分层

会让 MVP 启动成本太高，不适合当前阶段。

## 推荐执行顺序

### 第一阶段：正式冻结规格
1. 建立 `docs/README.md`
2. 冻结目录结构文档
3. 冻结数据库 V1 文档
4. 冻结领域模型文档
5. 记录 ADR

### 第二阶段：建立代码骨架
1. 创建 `frontend/`
2. 创建 `backend/`
3. 搭建 React + Vite 基础环境
4. 搭建 Spring Boot + MyBatis-Plus 基础环境
5. 确定数据库 migration 方式

### 第三阶段：打通 MVP 闭环
1. 首页歌曲列表
2. 歌曲详情页
3. 播放器
4. 搜索
5. 登录
6. 收藏
7. 歌单

### 第四阶段：增强能力
1. 完善三语内容支持
2. 优化 PostgreSQL 搜索能力
3. 再考虑 Agent 接入
4. 最后考虑 React Native Android 端

## 本轮完成后应继续做的事

### 立即下一步
- 决定数据库 migration 工具
- 建立 `frontend/`、`backend/` 代码骨架
- 设计后端 API 清单

### 暂缓事项
- `agent-service/` 代码实现
- `mobile-app/` 代码实现
- 推荐系统
- 社区功能

## 当前未决问题

### 业务未决
1. 音频来源模型
2. 登录方式
3. 收藏范围是否只限歌曲
4. 搜索结果排序规则
5. 数据导入方式

### 数据建模未决
1. 歌单是否允许重复歌曲
2. 专辑与歌曲的版本关系细化程度
3. 作品关系类型枚举范围
4. alias 类型枚举范围

### 技术未决
1. Spring Boot 的 migration 工具选 Flyway 还是 Liquibase
2. 搜索第一版是否立即启用 `pg_trgm`
3. 前端 UI 组件库是否引入

## PostgreSQL 学习提示

后续实现时，数据库部分建议你重点先理解这几件事：
- `identity` 主键
- `timestamptz`
- `text`
- `boolean`
- `ILIKE`
- `pg_trgm`
- `GIN`

你不需要一次全懂，我会在后续落地表结构和查询时继续带着你理解。
