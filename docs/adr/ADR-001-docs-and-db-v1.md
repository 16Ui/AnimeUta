# ADR-001：文档分层与数据库 V1 方案

## 状态
已接受

## 背景

AnimeUta 当前仍处于项目蓝图阶段，尚未创建实际业务代码。

已明确的信息包括：
- 产品定位：以 ACG 歌曲为核心的三语音乐软件
- 第一阶段优先 Web
- 技术栈：React + Java + PostgreSQL + MyBatis-Plus
- 后续扩展：Agent 与 React Native Android

在进入代码实现前，需要先冻结：
- 项目目录结构
- 数据库第一版边界
- 文档主规范位置

## 决策

本轮采用：

1. **分层文档方案**
   - `CLAUDE.md` 继续作为蓝图摘要与 AI 快速上下文
   - `docs/` 作为团队协作主规范

2. **混合型数据库设计**
   - 主实体表使用直列多语言字段
   - 多对多关系使用关系表
   - 搜索能力通过 alias 表预留扩展位
   - 不在第一版引入通用翻译表与独立搜索投影表

## 选择理由

### 为什么要分层文档
如果所有内容都只放在 `CLAUDE.md`，后续文档会越来越重，也不利于团队协作和正式规格维护。

### 为什么不做极简数据库
极简数据库虽然快，但在歌曲、作品、专辑、收藏、歌单、多语言搜索这些场景下会快速返工。

### 为什么不做完全规范化数据库
当前项目仍处于 MVP 规划阶段，过早引入重度规范化会提高实现与维护成本，不适合现在的节奏。

## 被放弃的方案

### 方案 A：单文档 + 极简数据库
放弃原因：
- 后续返工概率高
- 搜索与关系建模能力不足

### 方案 B：完全规范化数据库 + 重文档体系
放弃原因：
- MVP 成本过高
- 当前阶段收益不足

## 影响

### 正向影响
- 文档结构清晰
- 数据库边界明确
- 后续前后端实现有稳定依据
- 适合渐进式扩展到搜索、Agent、移动端

### 潜在副作用
- 未来语言数继续增长时，直列字段可能需要重构
- 若文档维护不及时，`CLAUDE.md` 与 `docs/` 可能出现双源分叉
- 某些未决业务规则仍可能导致数据库字段调整

## 后续动作

1. 建立前后端代码骨架
2. 设计后端 API 清单
3. 确认 migration 工具
4. 明确未决业务规则
