# 数据库 Schema V1

## 设计目标

第一版数据库需要支持以下 MVP 能力：
- 歌曲浏览
- 歌曲详情
- 搜索
- 收藏
- 歌单
- 基础用户系统
- 三语内容展示

本版本采用：
- 分层文档
- 混合型数据库设计
- PostgreSQL 优先思维
- 关系清晰优先于过早抽象

## 先给你的 PostgreSQL 指南

因为你对 MySQL 比较熟，所以这里先用你容易理解的方式讲。

### 1. 主键
在 MySQL 里你可能习惯 `AUTO_INCREMENT`。

在 PostgreSQL 里，这一版我建议你优先理解成：
- 主键用 `bigint`
- 自增推荐 `generated by default as identity`

也就是说，思路和 MySQL 类似，但 PostgreSQL 推荐写法不同。

### 2. 时间字段
在 MySQL 里很多人习惯直接上 `datetime`。

在 PostgreSQL 里，这一版建议优先考虑：
- `timestamptz`

原因是它更适合时区场景。你可以先简单理解为：
> 存储时更适合跨地区系统，不容易后面补救。

### 3. 文本字段
MySQL 里很多人喜欢到处写 `varchar(255)`。

PostgreSQL 里很多普通文本字段直接用 `text` 就可以，不需要为了“长度焦虑”乱设上限。

### 4. 布尔值
不要用 MySQL 思维里的 `tinyint(1)`。

PostgreSQL 直接就是：
- `boolean`

### 5. 搜索
PostgreSQL 在搜索上比 MySQL 更有优势。

第一版你需要先记住三个关键词：
- `ILIKE`：大小写不敏感模糊匹配
- `pg_trgm`：更强的模糊匹配能力
- `to_tsvector + GIN`：全文搜索能力

第一版不需要一次全上，但文档要先按这个方向设计。

## 约束与删除策略建议

### 外键
第一版建议所有关系表都使用外键，保持数据完整性。

### 删除策略
建议：
- 主体表删除优先 `restrict`
- 纯关系表删除可考虑 `cascade`

简单理解：
- 核心数据不要轻易级联删掉
- 关系挂件可以随主体删除而删除

## 枚举字段策略

第一版建议：
- 用 `varchar + check` 约束
- 暂不急着上 PostgreSQL enum

原因：
- 更灵活
- 后期改枚举成本更低
- 更适合当前仍在定边界的阶段
